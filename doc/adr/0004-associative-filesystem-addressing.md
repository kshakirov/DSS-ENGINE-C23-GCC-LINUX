# 0004. Ассоциативная файловая система: адресация через свойства и запросы

* Status: Accepted
* Date: 2026-08-29

## Context

Традиционная файловая система предоставляет пользователю преимущественно иерархическую модель адресации:

```text
/path/to/object
```

Даже если физическая идентичность объекта отделена от pathname, пользовательская модель остаётся пространственной: объект считается находящимся в некотором месте дерева.

Для DSS этого недостаточно. Цель проекта — исследовать файловую систему, в которой объект не обязан иметь единственное привилегированное местоположение, а может обнаруживаться по различным признакам и их комбинациям.

Важно: новая модель не должна превращаться просто в графовую файловую систему. Замена дерева графом меняет структуру связей, но не сам принцип адресации. DSS должен исследовать именно **ассоциативную адресацию**.

## Decision

### 1. Идентичность объекта отделяется от способа доступа

Объект существует независимо от имени, пути или конкретного набора признаков, по которым он был найден.

Условно:

```text
ObjectId -> Object
```

а способы доступа образуют отдельный слой:

```text
association/query -> one or more objects
```

### 2. Path не запрещается, но теряет привилегированный статус

Традиционный путь может существовать как один из способов именования или поиска:

```text
/books/math/lie/algebra.pdf
```

но семантически он не важнее других ассоциаций, например:

```text
name = "algebra.pdf"
author = "..."
subject = "Lie algebra"
content_hash = ...
created_after = ...
```

Путь становится частным случаем ассоциации, а не фундаментом пространства имён.

### 3. Поиск становится формой адресации

Базовая операция файловой системы мыслится не только как:

```text
path -> object
```

а в более общем виде:

```text
Q(P) -> { O1, O2, ... On }
```

где `P` — условие или описание желаемого объекта.

Такой запрос может вернуть один объект, несколько объектов или пустое множество.

### 4. "Директория" может быть представлением сохранённого запроса

Каталог не обязан существовать как физический узел дерева.

Он может интерпретироваться как сохранённый предикат:

```text
D = { x | P(x) }
```

При открытии такого представления система вычисляет множество объектов, удовлетворяющих условию.

Это не отменяет привычные директории как UI-представление, но лишает их обязательного статуса в модели хранения.

### 5. Реализация индекса не фиксируется этим решением

Ассоциативная модель определяет семантику доступа, но не предписывает внутреннюю структуру данных.

Для реализации могут применяться разные механизмы:

- плотные массивы;
- open addressing / Robin Hood hashing;
- inverted indexes;
- Bloom/Cuckoo filters;
- content hashes;
- специализированные индексы по отдельным признакам.

Эти структуры являются физическими средствами реализации запроса, а не моделью файловой системы.

## Layering

Предварительная архитектурная цепочка:

```text
Associative object model
        |
        v
Associations / predicates / queries
        |
        v
Object resolution
        |
        v
Content
        |
        v
CDC / Rabin fingerprinting
        |
        v
Deduplication index
        |
        v
Physical blocks / storage
```

Ассоциативный слой отвечает на вопрос:

> Как обнаружить объект?

Нижний storage-слой отвечает на другой вопрос:

> Как физически хранить содержимое и не сохранять одинаковые блоки повторно?

Эти задачи связаны, но не должны смешиваться.

## Consequences

### Positive

- файловая система перестаёт быть логически привязана к дереву;
- один объект может иметь множество равноправных способов обнаружения;
- поиск становится встроенной частью адресации, а не внешней утилитой поверх файловой системы;
- path сохраняется для совместимости и удобства, но становится частным случаем общей модели;
- внутренние структуры индекса можно свободно менять без изменения семантики системы.

### Negative / Open questions

Решение пока сознательно не определяет:

- точную структуру `ObjectId`;
- минимальный набор типов ассоциаций;
- язык запросов;
- правила уникальности и разрешения неоднозначности;
- модель изменения и удаления ассоциаций;
- механизм персистентного хранения самого ассоциативного индекса;
- границу между "признаком объекта" и традиционными "метаданными".

Эти вопросы должны решаться последовательно по мере реализации.

## Guiding principle

> Объект не обязан иметь единственное местоположение. Объект обладает множеством признаков, любой допустимый набор которых может служить способом его обнаружения.
