# 1. Выбор механизма управления контекстом и кооперативной многозадачности

* **Дата:** 25 июля 2026 г.
* **Статус:** Принято
* **Автор:** kshakirov

## Контекст
Для реализации высоконагруженного движка хранения требуется легковесная многозадачность («зеленые потоки» / корутины), чтобы дисковые операции ввода-вывода не блокировали системные потоки ОС. Стандартные функции Си `setjmp`/`longjmp` не позволяют выделять изолированные стеки для параллельных подзадач, а использование тяжелых системных потоков (`pthread`) неэффективно с точки зрения ТМО (Теории массового обслуживания) из-за накладных расходов на контекст-свитч ядра.

## Решение
Реализовать полунеявную схему переключения контекста (Yield) с ручным управлением регистрами процессора через встроенный ассемблер GCC (`__asm__` в x86-64).

Диспетчер динамически сохраняет указатель на свой стек (`RSP`) в Thread-Local переменную потока (`thread_local void* dispatcher_rsp`) непосредственно перед активацией корутины. Функция уступки кванта времени `fiber_yield()` вызывается из бизнес-логики без передачи параметров и совершает прыжок напрямую по этому сохраненному адресу.

## Последствия
* **Плюсы:** 
  * API функций хранения полностью очищен от инфраструктурных указателей на планировщик.
  * Исключены глобальные переменные процесса (безопасно для многопоточного рантайма).
  * Максимальная скорость переключения (сохраняются только callee-saved регистры).
* **Минусы:**
  * Жесткая привязка к архитектуре x86-64 и System V AMD64 ABI.
  * Необходимость ручной разметки фрейма стека при инициализации корутины.
